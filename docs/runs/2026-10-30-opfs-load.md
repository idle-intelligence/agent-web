# 2026-10-30: agent-wasm loading a GGUF from OPFS, memory and resume

## Parameters

- Builds:
  - old: agent-wasm at d771e52 (lean 4ce38c4), `agent_wasm_bg.wasm` `32fbc552...`. `Agent.load` takes a `Uint8Array` and copies it into wasm memory (`GgufSource::Bytes(gguf_bytes.to_vec())`).
  - new: this branch on lean with `OpfsReader`, `agent_wasm_bg.wasm` `cf8b32ae...`, `opfs-gguf.js` `b22f7e9f...`. `Agent.load` takes a `Uint8Array` (read one tensor at a time, no copy) or a `FileSystemSyncAccessHandle`.
- `opfs-gguf.js` in the commit differs from the served `b22f7e9f...` only by a comment on `askPersist`.
- The page called `askPersist()` before starting the worker; in the Chromium runs it waited for the answer (denied, `persisted: false`), in the Firefox runs it did not wait.
- Served bytes: each run's page fetched its files with `?v=cf8b32a`; the served `agent_wasm_bg.wasm` and `opfs-gguf.js` were hashed with curl before every run and matched the builds (`data/2026-10-30-opfs/summary.json:<run>.servedSha256`).
- Modes, all in a dedicated module worker:
  - old: old build, GGUF fetched whole (`fetch().arrayBuffer()`), passed as a `Uint8Array`.
  - bytes: new build, same `Uint8Array`.
  - opfs: new build, `downloadGguf(url, {sha256})` into OPFS (Range requests of 64 MiB, written at their offsets, SHA-256 hashed as the bytes arrive), the handle passed to `Agent.load`, then closed. "opfs, download" is a fresh profile; "opfs" is the second visit with the file already in OPFS.
- Models: Qwen3-1.7B Q8_0 (1,834,426,016 bytes, SHA-256 `061b54da...`) and Qwen3-4B Q4_0 (2,369,547,040 bytes, SHA-256 `11f1ec4b...`), served from localhost with HTTP Range support; tokenizer files from the Qwen3 releases; `maxCtx` 1024, `maxNewTokens` 64, thinking off.
- Prompt: system "You are a helpful assistant. Answer in one short sentence.", user "What is the capital of France?", no tools.
- Machine: the Linux test machine (RTX 3080), Playwright's bundled Chromium 153.0.8010.12, headless, Vulkan flags; `requestAdapter()` vendor `nvidia`, architecture `ampere` in every run. One fresh persistent profile per run except where a run reuses the previous one (resume, second visit). Nothing else ran on the GPU.
- Memory: renderer `VmHWM` (peak resident set of the renderer process, which hosts the worker) and GPU-process `VmHWM` from `/proc` at the end of the run; the worker's JS heap (`usedSize`) and ArrayBuffer backing stores (`backingStorageSize`) from CDP `Runtime.getHeapUsage` on the worker target, sampled every 200 ms (sampled peaks); wasm memory is `memory.buffer.byteLength` after `Agent.load`.

## Observations

- With the old build, the renderer peaked at 5,390 MiB for a 1,749 MiB file: the fetched `Uint8Array` (backing peak 2,572 MiB, which includes wasm memory) plus a 2,512 MiB wasm memory holding the copy.
- Passing the same `Uint8Array` to the new build drops wasm memory to 763 MiB and the renderer peak to 3,691 MiB; the JS copy of the file remains.
- With the handle, no buffer of the file's size exists in JS or wasm: the renderer peak is 1,625 MiB for the 1.7B and 1,569 MiB for the 4B, below the 4B file size (2,260 MiB).
- wasm memory after an OPFS load (763 MiB for the 1.7B, 696 MiB for the 4B) is larger than the largest tensor (`token_embd`: 315 MiB for the 1.7B, 209 MiB for the 4B) and the same for the 1.7B with the `Uint8Array`: it comes from the loader and the rest of the engine, not from the reader.
- The old path cannot load the 4B at all: one `ArrayBuffer` of 2,369,547,040 bytes is over Chromium's limit, and `fetch().arrayBuffer()` fails.
- `Agent.load` times of the four 1.7B runs are within 213 ms of each other (single runs).
- On the CPU backend the model itself lives in wasm memory (2,315 MiB in Firefox for the 1.7B, either source); the OPFS path removes only the JS copy there.
- The download resumed from the last flushed 64 MiB chunk after the browser was closed mid-chunk, and the streamed SHA-256, carried across the interruption in the progress record, matched the file's.
